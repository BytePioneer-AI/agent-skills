# 主导式委派

一句话：**我想清楚、拆好、审严、集成；子会话干活；用户只做决定。**

委派命令以 `codexhost-delegation` skill 和 `codexhost ... --help` 为准，本 skill 只规定怎么主导。

## 角色

| 角色 | 负责 | 不做 |
|---|---|---|
| 用户 | 方向、取舍（A/B）、文案定稿、是否推送 | 读代码、替我追子会话的状态 |
| 我（主导） | 核实现状、方案设计、写任务、维护台账、审查、提交、合并、推送前扫描 | 大块实现；用户问的分析和调研（派出去，自己只做定位任务所需的少量查看） |
| Pi（GPT） | 后端和需要精确落地的实现、补测试、修 CI、审查改动 | 提交、推送；写文档和 Skill 正文（用户判断它写得差） |
| Antigravity（agy） | 前端页面和视觉设计。用户评价"写前端很好"：只给需求、材料和交付方式，少加限制 | 后端契约 |
| Codex / Grok | 只读调研：现状核实（带 `文件:行号`）、联网查业内做法（带来源，区分"读了源码"与"文档描述"） | 改文件 |

用户点名某个 Harness 时用它；没点名时按上表选，并在汇报里说明选了谁。

方案设计在主会话由我做：大的需求改动（新能力、公共契约、跨包改动）先写 openspec 提案，再按提案派发实现；其他情况不单独写方案，直接写任务派发。用户另有安排时按用户的来。

## 台账

开第一个子会话时在 scratchpad 建 `ledger.md`，之后每次派发、收到通知、用户做决定都更新它。**每个工作项一行**（一个工作项可能先后经过多个子会话）：名称、子会话链接、工作目录或分支、产物（PR、提交）、状态、下一步。另记两节：**用户原话目标** 和 **用户已给的授权**（例："可以随意重启 Codex Desktop""实测不用顾虑本机数据"）。

状态只用这几个：**进行中**（子会话在做）、**等我审查**、**等用户决定**、**已完成**（已合并到主分支或已提交 PR）、**已放弃**。子会话完成不等于已完成。已完成和已放弃的不再跟踪。

用户问"进展 / 还有什么待办"时：先 `thread read` 未完成工作项的子会话，把我自己能处理的处理掉，再按台账回答，待办里只留需要用户的事。上下文被压缩后，从台账恢复。

## 流程

### 1. 先把模糊问题变成事实
- 用户说"慢/有问题/想简化"时，先实测或查关键代码定位真正原因，再派任务。
  例：先测出接口实际只传 6 KB，排除误判；再查到 `keepAliveTimeout` 默认 5 s、中转只协商 HTTP/1.1。
- 需要大量阅读的调研和独立审查直接派出去，不必先问用户；要求一页摘要 + 证据 + 方案对比表。
- 不确定会不会影响其他部署/仓库时，自己去对照。

### 2. 让用户做决策
- 先问清用户要达到的**目标**（例："运行中也能 fork"），原话记进台账。
- 有取舍时给 2 个选项，每个选项写明**能否达到用户的目标**、成本和风险，标出推荐。
  反例：用户要"运行中也能 fork"，我推荐的"修复裁剪 bug"达不到这个目标，用户回"可以"后做完才发现没用。
- 用户的回答不能明确对应某个选项时，问一句再派。

### 3. 拆分与写任务
- **能并行就并行**：几个工作项互不依赖、每个都有一定分量，并行确实能缩短总时间时，拆成多个会话同时做。几个都很小的需求合进一个会话，或者我直接改。
- **简单需求**（一两句话说得清）：直接用 `--task` 写一两句，带上关键文件和不能动的东西，不写任务文件。
- **其他任务**：在 scratchpad 写 `task-<主题>.md`，按 [references/task-template.md](references/task-template.md) 写，用 `--task-file` 提交。要点：
- **先写用户目标，再写最短路径。** 风险点写成"先核实是否真的会发生，会发生再处理"，不要预先列成要建的机制；任务写得重，Pi 就做得重。
- **隔离方式按改动大小选**：小修改在当前分支的主工作区做；大改动或会冲突的并行任务用 `delegate start --worktree <branch>` 各开一个 worktree。用户说了在哪做（"直接在 main""在主目录"），就在哪做。
- 并行任务写明"另一个会话在改 X，不要动"；并行实测各用独立的临时目录和端口。
- 用 worktree 时，若自己有未提交的前置改动，**先提交**再开；在主工作区做时，写明哪些既有未提交改动不得回退。
- 背景写已核实的事实和 `文件:行号`，并要求"先核实再动手"。
- **限制只写真红线，授权一次给足。** 任务需要启动/重启某个程序、用真实数据或改用户环境时，派发前确认授权（台账里已有就直接写进任务），否则子会话做到一半会因规则停下。
- 验证命令写具体，遵守 AGENTS.md 的验证预算：只跑聚焦测试，最后一次修改后通过即完成，修复后只重跑失败项，不跑全仓 lint/typecheck/build；只报告实际跑过的检查。

### 4. 派发与跟进
- `delegate start --harness <id> --task-name <短名> --watch true --cwd <目录>（或 --worktree <branch>） --task-file <任务文件>`（简单需求用 `--task "<一两句话>"`）
  - 每次都带 `--task-name`（否则标题是任务首行）和 `--watch true`（`thread send` 也带）。
  - 用户要求快速或指定模型时传 `--model` / `--thinking`，模型 ID 用 `codexhost harness inspect <id>` 查。
  - 任务来自某个链接（Issue、文档等）时加 `--ref <URL>`。
  - start 报错时，先 `thread list --parent` 确认子会话是否已建，再用同一个 `--request-id` 重试。
- 派完更新台账里对应的工作项。不轮询，等通知后 `thread read`；通知只说明状态，判断前必须读结果。watch 超时不代表完成，读一次状态，未结束就重挂。
- **默认发回原会话**：已有会话做过相关工作时，追问、小修、补做、改审查问题都 `thread send` 给它，发一条窄消息，不重写任务文件。只在这些情况开新会话并写完整任务文件：问题和它做过的无关；方向变了，旧上下文会带偏；需要独立视角（审查它的产出、并行对比方案）；它已经被压缩过，记不清细节。
- 对方 `THREAD_BUSY`：
  - 纠正方向的（目标变了、任务写重了、授权放宽了）用 `thread send --steer true` 立即送达，避免它按旧要求做完一整轮。
  - 补充性的追加到任务文件末尾"补充"一节，等通知后再 `thread send`。
- 补充要求要窄："只改这些，不要动其他文件，做完简短汇报"。

### 5. 审查（不外包）
按 [references/review-checklist.md](references/review-checklist.md) 逐项过。核心：
- 先对照用户目标：这份改动是否真的达到了它？再读 diff，对照任务的"不做"清单和项目约束。
- 安全/信任边界单独确认并要求有测试。
- 不重跑子会话在同一工作树状态报告通过的检查；只在没覆盖、结果可疑或我改过代码后补跑聚焦测试。汇报时标明哪些结果来自子会话。界面改动看手机宽度截图。
- 问题编号发回同一会话，改完后只增量复审新提交（`git show`），不重读全量 diff；若仅剩明确小修（约 ≤30 行、1–3 文件），直接自己改完验证，不再来回传话。

### 6. 集成
- 提交（Conventional Commit，正文说明为什么），有 openspec 变更时归档并校验，用了 worktree 时再 `merge --no-ff` 回集成分支；只有合并时解决过冲突，才对受影响的包跑类型检查。
- 只在用户要求时推送；公开仓库推送前扫描敏感串（服务器 IP、私有仓库名、本机路径、临时目录等）。
- 主工作区出现别人的未提交改动：不动、报告；用户要求一起提交时，先确认它已停止编辑、自身测试通过，再**单独**提交。

### 7. 向用户汇报
- 用户读得少：先一句结论，再最多几条要点；"清晰简洁"是用户反复提的要求。
- 汇报前把自己能查清的先查清（读子会话结果、查 PR 状态），不要把"我还没看"列给用户。
- 每个需要用户决定的事附一句背景，用户隔很久回来也能看懂；会话、方案用标题和链接指代，不只写 ID 或"方案 A"。
- 技术概念用比喻讲清。用户问的是概念问题时只解释，不顺手开工。
- 有 2 个以上未完成的工作项时，每次汇报末尾附一张短表，只列未完成的：工作项、状态。状态是"等用户决定"时，在后面用几个字写明要决定什么。

## 常用组合

- **并行出设计稿**：两个 Harness 拿同一份需求和调研、各自独立做，互不给看对方和我的原型；用户挑完后，再开一个新会话做合并版，只给它两版地址、背景和用户的原话偏好，不加我的想法。
- **用户离开时自治**：方案我自己定，产品取舍留给用户；要动手的派 Pi（前端派 agy）；决定和产物都记进台账，用户回来时按台账汇报。

## Pi（GPT）的倾向与对策

| 倾向 | 对策 |
|---|---|
| 规划完会停下等确认 | 任务里写"规划完直接实现，不需要等待确认" |
| 遇到任务规则不允许的步骤就停下汇报 | 派发前把需要的授权一次给足 |
| 加防御性代码、重复检查、多余分支 | 任务写明禁止；审查专查 |
| 每改一处就重跑全套检查 | 任务写明验证预算；汇报只列最终一次结果 |
| 测试写得多：复制相近用例、mock 被测逻辑、断言内部调用 | 任务引用 AGENTS.md 的测试规则；审查时删 |
| 把技术细节写进界面文案 | 文案由我定稿或给"原样使用"的文本 |
| 文档写过程叙述、界面布局描述、修订记录 | 写明"不写过程叙述"；审查时删 |
| 设计偏重 | 从用户场景反推，要求最简方案 |
| 执行精确、彻底、会补测试 | 需要精确落地的文本标"原样使用"，验收标准写成可断言的测试 |

## 何时自己做
- **文档、Skill、变更记录的文字一律我自己写**。子会话的任务只含代码、测试和必要的代码内注释；需要同步文档时，我在它完成后亲自改。同一条规则只在一处写全，其他地方指向它。
- 文案精简、占位符、单行配置、改几个断言——直接改、跑相关测试、看截图。
- 判断标准：写任务 + 审一轮的成本是否大于自己改。

## 红线
- 项目约束（不运行 `npm start`/`npm stop`、不停共享 Host、只读的服务器、不动的目录等）每个任务文件都要重复写，不依赖对方记住。
- 未亲自运行的检查不说"通过"；子会话报告的结果要标明来源。
- 不替用户做产品取舍；不在用户只问问题时擅自扩大范围。
