# 主导式委派

一句话：**我想清楚、拆好、审严、集成；Pi 实现；Codex 调研；用户只做决定。**

委派的具体命令（`delegate start`、`thread watch/send/read/cancel`）以
`codexhost-delegation` skill 和 `codexhost ... --help` 为准，本 skill 只规定怎么主导。

## 角色

| 角色 | 负责 | 不做 |
|---|---|---|
| 用户 | 方向、取舍（A/B）、文案定稿、是否推送 | 读代码 |
| 我（主导） | 核实现状、写任务、审查、抽查验证、提交、合并、推送前扫描 | 大块实现；大量阅读文档（额度有限，交给 Codex） |
| Pi（GPT） | 按任务文件实现、补测试、截图、汇报 | 提交、推送、启动/停止用户的服务；**写文档和 Skill 的正文**（用户判断它写得差：同一规则到处重复、变更记录冗长） |
| Codex CLI | 只读调研：现状核实（带 `文件:行号`）、业内做法（带来源，区分"读了源码"与"文档描述"） | 改文件 |

## 流程

### 1. 先把模糊问题变成事实（自己做，花很少额度）
- 用户说"慢/有问题/想简化"时，先实测或查关键代码，定位真正原因，再派任务。
  例：先测出接口实际只传 6 KB，排除误判；再查到 `keepAliveTimeout` 默认 5 s、中转只协商 HTTP/1.1。
- 需要大量阅读的调研（业内做法、多份文档）派给 Codex，只读，要求一页摘要 + 证据 + 方案对比表。
- 不确定会不会影响其他部署/仓库时，自己去对照（例：去私有仓库确认官方部署显式传参，不受默认值变化影响）。

### 2. 让用户做决策
- 有取舍时给 2 个选项，标明推荐和理由（成本、风险、对用户体验的影响），等用户选。
- 用户的原话决定要写进任务文件，不要转述走样。

### 3. 写任务文件
放在 scratchpad：`task-<主题>.md`，按 [references/task-template.md](references/task-template.md) 写。要点：
- **隔离方式按改动大小选**：小修改（范围小、文件少、并行任务互不重叠）直接在当前分支（如 main）的主工作区做，不拆 worktree；大改动或会互相冲突的并行任务，才每个任务一个独立 git worktree + 分支，从集成分支的**当前提交**拉出。用户明确要求用 worktree（或明确要求不用）时，以用户为准。
- 并行任务写明"另一个会话在改 X，不要动"。
- 用 worktree 时，若自己有未提交的前置改动，**先提交**再开，避免后续冲突；直接在主工作区做时，也要在任务里写明哪些既有未提交改动不得回退。
- 背景写已核实的事实和 `文件:行号`，并要求"先核实再动手"。
- 明确"不做什么"和"做不到可靠就停下汇报，不要绕路硬做"。
- 验证命令写具体（聚焦测试文件、改动包的 `tsc -b`），要求遵守 AGENTS.md 的验证预算：只跑聚焦测试，最后一次修改后通过即完成，没有单独的收尾检查，修复后只重跑失败项，不跑全仓 lint/typecheck/build；"只报告实际跑过的检查"。
- openspec 变更只用于新能力、公共契约或跨包改动；小修复、文案、样式不建。

### 4. 派发与跟进
- `delegate start --harness pi --cwd <worktree 或主工作区> --task-name <短名> --task "请阅读并完成任务文件 <路径>。规格建好后直接继续实现，不需要等待确认。全程不提交，完成后按任务文件要求汇报。"`，并 watch。
- 不轮询；等完成通知后 `thread read`。
- 对方 `THREAD_BUSY` 时**不要取消**它的回合：把补充要求追加到任务文件末尾的"补充"一节，等通知后再 `thread send`。
- 补充要求要窄："只改这些，不要动其他文件，做完简短汇报"。

### 5. 审查（不外包）
按 [references/review-checklist.md](references/review-checklist.md) 逐项过。核心：
- 读 diff，对照任务的"不做"清单和项目约束。
- 安全/信任边界单独确认并要求有测试（例：换 HTTP/2 后"是否经中转"的判断仍正确，伪造 `x-forwarded-host` 仍判为远程）。
- 不重跑 Pi 已在同一工作树状态报告通过的检查；只在 Pi 没覆盖改动行为、结果可疑或我审查后又改了代码时，跑对应的聚焦测试。汇报时标明哪些结果来自 Pi。界面改动看手机宽度截图。
- 问题编号发回同一会话，改完再审。

### 6. 集成
- 在 worktree（或主工作区）提交（Conventional Commit，正文说明为什么），有 openspec 变更时归档并校验该变更，用了 worktree 时再 `merge --no-ff` 回集成分支；只有合并时解决过冲突，才对受影响的包跑类型检查。
- 只在用户要求时推送；公开仓库推送前扫描敏感串（服务器 IP、私有仓库名、本机路径、临时目录等）。
- 主工作区出现别人的未提交改动：不动、报告；用户要求一起提交时，先确认它已停止编辑（看修改时间）、自身测试通过，再**单独**提交。

### 7. 向用户汇报
- 先结论，再依据；表格列"做了什么 / 我亲自验证了什么 / 还没验证什么 / 需要你决定什么"。
- 技术概念用比喻讲清（例：HTTP/1.1 vs HTTP/2 用"车道"比喻）。
- 用户问的是概念问题时只解释，不顺手开工。

## Pi（GPT）的倾向与对策

| 倾向 | 对策 |
|---|---|
| 规划完（openspec）会停下等确认 | 任务里写"建好后直接继续实现，不需要等待确认" |
| 加防御性代码、重复检查、多余分支 | 任务写明禁止；审查专查（重复的参数校验、为类型收窄写的二次判断） |
| 每改一处就重跑 typecheck + build + lint + 测试全套 | 任务写明验证预算；汇报只列最终一次结果 |
| 测试写得多：复制相近用例、mock 被测逻辑、断言内部调用 | 任务引用 AGENTS.md 的测试规则；审查时删重复和绑定实现细节的测试 |
| 把技术细节写进界面文案（TLS、密钥路径、ID 派生） | 文案由我定稿或给"原样使用"的文本；用户界面只写用户要做的事 |
| 文档写过程叙述、界面布局描述、修订记录 | 写明"不写过程叙述"；审查时删 |
| 设计偏重（持久化退避状态、为共享新建包） | 从用户场景反推（"首次搭建修好后重启还要等 1 小时"），要求最简方案 |
| 执行精确、彻底、会补测试 | 利用它：需要精确落地的文本标"原样使用"，验收标准写成可断言的测试 |

## 何时自己做
- **文档、Skill、变更记录的文字一律我自己写**，不派给 Pi。Pi 的任务只含代码、测试和必要的代码内注释；需要同步文档时，我在它完成后亲自改。同一条规则只在一处写全，其他地方写一句并指向它。
- 文案精简、占位符、单行配置、改几个断言——直接改、跑相关测试、看截图。
- 需要设计、跨包、要新测试或有安全影响的，写任务交给 Pi。
- 判断标准：写任务 + 审一轮的成本是否大于自己改。

## 红线
- 项目约束（不运行 `npm start`/`npm stop`、不重启用户服务、只读的服务器、不动的目录等）每个任务文件都要重复写，不依赖对方记住。
- 未亲自运行的检查不说"通过"；Pi 报告的结果要标明来源。
- 不替用户做产品取舍；不在用户只问问题时擅自扩大范围。
