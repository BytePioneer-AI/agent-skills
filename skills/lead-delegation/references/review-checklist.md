# 审查清单

## 读改动
- [ ] `git status` + `git diff --stat`：改动范围是否超出任务；有无无关文件（依赖锁文件变化要有原因）。
- [ ] 逐个看核心源码 diff，对照任务的"不做"清单。
- [ ] 防御性代码：重复校验、为类型收窄的二次判断、不会发生的分支、吞掉的错误。
- [ ] 过度设计：没要求的持久化、配置项、新包/新抽象、每次请求新建本可复用的对象。
- [ ] 包边界与依赖方向（如 `tools/check-boundaries.mjs`）；新依赖是否必要、版本是否固定。

## 行为与兼容
- [ ] 对其他部署/调用方的影响（默认值变化、参数变为可选、端口/路径变化），必要时去对应仓库核对。
- [ ] 安全/信任边界：身份判断、认证、同源、仅本机可见的数据；要求有对应测试。
- [ ] 失败路径的用户体验：首次使用、重启后、网络未就绪时会怎样。
- [ ] 本地访问等"不应改变"的路径确实没变。

## 文案与文档
- [ ] 界面文案只写用户要做的事，无内部技术细节；中英文一致。
- [ ] 文档写现行行为，无过程叙述、界面布局描述、修订记录。
- [ ] 公开仓库无敏感信息。

## 抽查验证（不重跑 Pi 已报告通过的全套）
- [ ] 核对 Pi 报告的检查覆盖了 diff 触及的面；缺的补跑。
- [ ] 仅当 Pi 未覆盖、结果可疑或审查后又改了代码时，亲自跑对应的聚焦测试（界面改动先重建前端产物）。
- [ ] 界面：查看手机宽度截图。
- [ ] 可在本机安全验证的配置（如 `docker compose config`）实际跑一次。

## 结论
- 有问题：编号列出，每条说明"现象 → 用户影响 → 期望改法"，发回同一会话。
- 通过：提交 →（有 openspec 变更时）归档并校验 → `merge --no-ff`（解决过冲突才补跑受影响包的类型检查）→ 等用户指示再推送（推送前扫描）。
